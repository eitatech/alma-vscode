# Dual-Lens Critique: Dynamic Extension Document Display in Spec Explorer

**Feature**: 017-extension-docs-tree
**Date**: 2026-04-14
**Phase**: Post-implementation (all 23 tasks complete, 100% adherence)
**Artifacts reviewed**: spec.md, plan.md, tasks.md, retrospective.md, implementation source

---

## Product Lens (CEO/Product Lead)

### 3a. Problem Validation

**Verdict: Strong**

The problem is real and well-scoped. Extensions like V-Model, Retrospective, and Cleanup generate `.md` files into spec directories, but these were invisible in the Spec Explorer tree. Users had to manually browse the filesystem -- a clear workflow break.

- **Evidence**: The `retrospective.md` already exists in `specs/016-multi-provider-agents/` and was invisible before this feature.
- **Scope**: Appropriately narrowed to SpecKit only (not OpenSpec). This was correctly clarified.

No critique items.

### 3b. User Value Assessment

**Verdict: Solid with one gap**

| Item | Assessment |
|------|-----------|
| US1 (extra files as nodes) | Clear value, directly addresses pain |
| US2 (subfolder grouping) | Strong, prevents clutter for V-Model-style extensions |
| US3 (auto-refresh) | Nice-to-have, correctly prioritized as P3 |

**P-01** (Consider): The spec assumes extension-generated files are always markdown (`.md`). However, extensions may generate other formats too -- the V-Model extension's `extension.yml` references a `config-template.yml`, and the `contracts/` folder pattern already holds non-markdown files (YAML, JSON, TypeScript). The **adjacent code preview work** (adding JSON/YAML/TOML rendering) partially addresses this, but the spec's FR-008 explicitly says "Non-markdown files MUST be ignored." This was the right decision for scope control, but should be revisited as a follow-up: extension subfolders containing `.yml`/`.json` contract files are invisible in the tree.

**Severity: Consider** | Not blocking, but a natural next step.

### 3c. Alternative Approaches

**P-02** (Consider): The spec rejected reading `extension.yml` metadata in favor of pure filesystem scanning. This was pragmatic for V1, but creates a missed opportunity: `extension.yml`'s `defaults.output_dir` could provide richer folder labels (e.g., "V-Model Extension Pack" instead of "V model") and the `provides.commands` list could enable right-click context menu actions on extension documents (e.g., "Regenerate requirements spec"). Worth revisiting when extensions mature.

**Severity: Consider** | Future enhancement, not a V1 gap.

### 3d. Edge Cases & User Experience

**P-03** (Should-Address): The spec identifies 4 edge cases, but misses one: **what happens when an extension generates a file with the same name as a known doc** (e.g., an extension that generates its own `plan.md` or `research.md` inside a subfolder)? The current implementation handles this correctly at the top level (known files take precedence), but the edge case isn't documented.

**P-04** (Consider): No tooltip or description shows _which extension_ generated a document. A user seeing "Retrospective" in the tree has no context about its origin. The `extension.yml` has this info, but the filesystem-only approach can't surface it. Minor UX gap.

**Severity: P-03 Should-Address (document edge case) | P-04 Consider**

### 3e. Success Measurement

**P-05** (Should-Address): The success criteria (SC-001 to SC-004) are all functional/immediate. There are no **adoption metrics**: How many users actually click on extension documents? How often does auto-refresh trigger? These would help validate that the feature delivers real value beyond just "it works."

**Severity: Should-Address** | Add telemetry events for clicks on extension-document nodes.

## Engineering Lens (Staff Engineer)

### 4a. Architecture Soundness

**Verdict: Clean, well-structured**

The implementation follows existing patterns faithfully:
- `collectExtraFiles()` mirrors the existing checklist/contract folder scanning
- `getExtensionFolderChildren()` follows the same pattern as `getChecklistsFolderChildren()`
- New `contextValue` types registered in the handler map
- Constants at top level per Biome rules

No circular dependencies. Clean separation between adapter (data) and provider (presentation).

### 4b. Failure Mode Analysis

**E-01** (Must-Address): **Synchronous filesystem operations in the extension host**. Both `collectExtraFiles()` and `getExtensionFolderChildren()` use `readdirSync`/`statSync`. The plan states "No synchronous blocking of the extension host" as a constraint, yet the implementation uses synchronous fs operations. For typical spec directories (< 50 files), this is negligible. But if a user has a deeply nested extension output folder with hundreds of files, the extension host blocks during tree rendering.

The _existing_ code already uses sync fs in the same methods (checklists, contracts), so this is consistent. But the plan explicitly called it out as a constraint.

**Mitigation**: The existing code uses `await import("node:fs")` pattern for lazy loading in `getExtensionFolderChildren`, but the actual operations (`readdirSync`, `statSync`) are still synchronous. This is an inherited pattern, not a regression.

**Severity: Must-Address** | Either update the plan to remove the misleading constraint, or file a follow-up to convert to async `fs.promises` operations across all tree methods.

**E-02** (Should-Address): **No depth limit on recursive directory traversal**. The clarification explicitly chose "fully recursive regardless of depth." While practically safe (extension output is shallow), a symlink loop or a user accidentally placing a deep directory structure in a spec folder could cause a stack overflow in `directoryHasMarkdown()`. No cycle detection exists.

**Mitigation**: `readdirSync` will throw on permission errors, which is caught. But symlink cycles would cause infinite recursion.

**Severity: Should-Address** | Add a reasonable depth limit (e.g., 10 levels) as a safety valve, or detect symlinks.

### 4c. Security & Privacy Review

No new attack vectors. All operations are local filesystem reads within the workspace. No user input is used in path construction beyond what VS Code's workspace API provides. No concerns.

### 4d. Performance & Scalability

**E-03** (Consider): The file watcher glob `**/specs/**/*.md` will fire for _all_ markdown file changes in _any_ `specs/` directory in the workspace. For large monorepos with many spec directories, this could cause excessive debounced refreshes. The 2-second debounce mitigates this, but the watcher itself consumes OS file descriptor resources proportional to the number of matched paths.

**Severity: Consider** | Low risk for typical SpecKit projects; could be a concern in very large workspaces.

**E-04** (Consider): `collectExtraFiles()` rescans the entire directory on every `getChildren()` call. There is no caching. For the common case (< 20 files), this is fine. For specs with 100+ extension-generated files, each tree expansion triggers a full `readdirSync` + `statSync` per entry.

**Severity: Consider** | No action needed now; watch for performance complaints.

### 4e. Testing Strategy

**Verdict: Solid**

- 9 adapter unit tests cover known-file exclusion, extra file discovery, subfolder detection, empty folder filtering
- 17 provider unit tests cover rendering, icons, ordering, and file watcher
- 4 integration tests cover the full adapter-to-provider flow
- TDD strictly followed (verified failing before implementation)

**E-05** (Should-Address): **Missing edge case tests**:
1. No test for symlink handling in directory traversal
2. No test for a directory named like a known file (e.g., `spec/` folder) -- spec edge case 3
3. No test for very long filenames or special characters -- spec edge case 4
4. `getExtensionFolderChildren()` has no unit tests (the integration test mocks the adapter, so the recursive fs reading is not directly tested)

**Severity: Should-Address** | Add targeted edge case tests.

### 4f. Operational Readiness

**Verdict: Adequate**

- `console.error` for scan failures (observability)
- `console.debug` telemetry for doc counts (T020)
- File watcher disposed via `context.subscriptions`
- No alerting thresholds needed (client-side extension)

### 4g. Dependencies & Integration Risks

**E-06** (Must-Address, Constitution): The retrospective noted a minor finding (M1): **`getExtensionFolderChildren()` does not filter empty nested subdirectories**. FR-009 states "Empty subfolders MUST NOT appear in the tree." The adapter-level `directoryHasMarkdown()` check only runs at the top level. Inside an extension folder, any subdirectory (even empty ones) is shown as a collapsible node. This is a **requirement violation**.

**Severity: Must-Address** | FR-009 is not fully implemented for nested extension folders.

## Recommendation

**Implementation quality is high.** 100% spec adherence, strict TDD, clean architecture following existing patterns. Two must-address items:

1. **E-06 (FR-009 gap)**: Quick fix -- add `directoryHasMarkdown()` check before creating nested `extension-folder` items in `getExtensionFolderChildren()`. Estimated: 1-line change + 1 test.
2. **E-01 (sync fs constraint)**: Document the inherited pattern in the plan (the existing checklist/contract methods use the same pattern). Not a regression.

Suggested next steps:
- Fix E-06 immediately (requirement violation)
- Address E-02 and E-05 in a follow-up polish pass
- Track P-05 adoption metrics as a separate task
